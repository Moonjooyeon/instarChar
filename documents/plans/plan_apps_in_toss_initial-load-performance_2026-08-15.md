# 앱인토스 최초 접속 성능 개선 계획

## 목표

미니앱 최초 접속에서 즉시 보이는 시작 화면을 앱 전체 코드와 서버 상태 조회에서 분리하고, 인증 후 사용자 상태를 불필요하게 두 번 받지 않도록 개선한다.

## 가정

- 토스 반려 기준의 20초는 사용자가 미니앱을 연 뒤 정상적인 첫 화면을 확인하는 시간이다.
- 약관 동의와 차단 목록은 기존처럼 앱 기능 사용 전에 확인해야 하지만, 네트워크 오류가 무한 로딩으로 이어져서는 안 된다.

## 범위

1. 엔트리에서 경량 시작 화면을 먼저 렌더링하고, 전체 앱 코드는 지연 로드한다.
2. `/profile/state` 응답을 프로필과 구조화 상태에 함께 사용해 중복 요청을 제거한다.
3. 안전 상태 조회의 실패를 사용자에게 복구 가능한 상태로 표시한다.
4. 타입 검사, 도메인 테스트, 프로덕션 빌드로 코드 분할과 회귀를 확인한다.

## 제외 범위

- 토스 SDK 또는 로그인 정책 변경
- 데이터 모델·마이그레이션 변경
- 실제 토스 콘솔 성능 대시보드 수치 확인

## 성공 조건

- 앱 진입 직후 경량 시작 화면이 전체 앱 코드·API 완료와 무관하게 렌더링된다.
- 저장된 로그인 사용자는 `/profile/state`를 최초 부트스트랩에서 한 번만 요청한다.
- 안전 상태 요청 실패 시 로딩 화면이 계속 유지되지 않고 재시도 가능한 안내가 표시된다.
- 프런트엔드 타입 검사, 도메인 테스트, 빌드가 통과한다.

## 검증 결과

- `npm run typecheck`: passed
- `npm run test:domain`: passed (181 tests)
- `npm run build`: passed. 초기 엔트리 JS는 144.03KB(압축 47.46KB), 전체 앱 런타임은 별도 358.12KB 청크로 분리됨.
- `npm run build:toss`: passed. `ashwoodfriends-alive.ait` 생성 완료.
- 기존 실행 중인 프런트엔드 프로세스: not run. 포트 5179·4173에는 실행 중인 앱이 없었고, 프로젝트 규칙에 따라 새 프로세스를 시작하지 않았다.

## 검증하지 못한 것

- 토스 샌드박스와 실제 운영 환경의 최초 접속 시간은 기존 실행 프로세스에서 수동 확인이 필요하다.

## 남은 위험

- 서버 콜드스타트 또는 토스 WebView 네트워크 상태가 20초를 넘기면 클라이언트 최적화만으로는 기준을 보장할 수 없다.

## 다음 추천 작업

1. 토스 성능 대시보드에서 배포 후 p95 최초 접속 시간을 확인한다.
2. 기준 미달이면 API 서버의 콜드스타트와 `/auth/me`, `/profile/state` 서버 시간을 각각 계측한다.

# 추천·팔로잉 피드 단계적 로드

## Problem

공유 캐릭터 탐색은 최대 80명을 한 번에 불러오고, 추천과 팔로잉 피드는 해당 캐릭터의 공개 게시글을 모두 한 번에 렌더링한다. 캐릭터와 글이 늘면 초기 로딩과 화면 렌더링 비용이 함께 증가한다.

## Outcome

추천과 팔로잉 탭은 처음 20개의 게시글만 표시한다. 사용자가 목록 하단에 도달하면 다음 20개를 자동으로 추가 표시하며, 더 불러올 항목이 없으면 끝 상태를 보여 준다.

## Evidence

- 서버 탐색 조회는 공유 캐릭터 80명으로 제한된다: `backend/app/repositories/shared_characters.py`의 `_shared_characters`.
- 공유 캐릭터별 공개 게시글 스냅샷은 최신 30개다: `apps/frontend/src/hooks/useAliveFeed.ts`의 `publicPostSnapshot`.
- 추천 및 팔로잉 탭은 각각 계산된 전체 게시글 배열을 그대로 렌더링한다: `apps/frontend/src/hooks/useAliveFeed.ts`와 `apps/frontend/src/app/feed/FeedTimeline.tsx`.
- 현재 커서, 페이지 번호, IntersectionObserver 기반 추가 로드는 없다.

## Assumptions and decisions

- 첫 묶음과 후속 묶음은 20개 게시글로 한다.
- 별도 페이지 버튼 대신 하단 감지 자동 로드(무한 스크롤)를 사용한다.
- 첫 단계는 이미 받아 온 추천·팔로잉 배열을 화면에서 나누어 표시한다. 서버 조회 API의 커서 페이지네이션은 후속 단계로 분리한다.
- 탭을 바꾸거나 활성 캐릭터를 바꾸면 각 탭의 표시 개수를 초기화한다.

## Scope

- 추천 및 팔로잉 탭에 공통 표시 개수 상태와 하단 감지 요소를 추가한다.
- 로딩 중, 더 불러올 항목 없음 상태를 접근 가능한 안내 문구로 표시한다.
- 추천/팔로잉 배열이 갱신될 때 중복이나 누락 없이 다음 묶음이 이어지도록 한다.
- 관련 도메인 또는 UI 테스트를 추가한다.

## Non-goals

- 내 글 탭의 페이징
- 게시글 작성·공유 동기화 방식 변경
- 서버의 공유 캐릭터 탐색 80명 제한 변경
- 새 외부 라이브러리 도입

## Acceptance criteria

- 추천과 팔로잉 탭은 각각 처음 20개만 렌더링한다.
- 목록 하단 도달 시 20개씩 추가 렌더링된다.
- 마지막 묶음 뒤에는 추가 요청/렌더링이 반복되지 않는다.
- 탭 또는 활성 캐릭터 전환 후 이전 탭의 표시 개수가 남지 않는다.
- 기존 추천 정렬, 팔로잉 시간순 정렬, 좋아요와 댓글 동작은 유지된다.

## Risks and next mode

- 이 단계는 이미 메모리에 받은 데이터만 나누어 보여 주므로, 네트워크 전송량 자체는 줄지 않는다.
- 공유 캐릭터 수가 80명을 넘어서는 실제 서버 페이지네이션은 별도의 API 계약 변경이 필요하다.
- 다음 단계: `alive-engineering-workflow`의 Change 모드로 최소 UI 구현과 도메인 테스트를 진행한다.

# 앱 전반 기능 개선 작업 계획

## 1. 목적

다음 사용자 경험과 운영 문제를 두 단계로 개선한다.

- 오래된 게시글의 상대 시간을 읽기 쉬운 단위로 표시한다.
- 캐릭터 관계 UI에는 실제로 등록되거나 연결된 다른 캐릭터만 표시한다.
- 자율 게시글 생성을 브라우저 타이머가 아닌 백엔드 스케줄러가 담당하게 한다.
- 사용자 페르소나 기능을 데이터 삭제 없이 앱에서 임시 비활성화한다.
- 테스트·개발 편의용 기능을 사용자 화면과 운영 흐름에서 제거한다.
- 이미지 저장을 외부 오브젝트 스토리지로 이전하는 작업은 Phase 2로 분리한다.

## 2. 용어와 범위 해석

### 사용자 페르소나와 캐릭터 페르소나 구분

이번에 비활성화할 대상은 사용자가 별도의 인물로 캐릭터에게 말하는 `UserPersona` 기능이다.

- 비활성화 대상: 홈의 내 페르소나 관리, DM의 내 페르소나로 말 걸기, DM 발화자 선택, 피드 댓글의 페르소나 선택, 페르소나 생성·수정 모달
- 유지 대상: 캐릭터 성격을 뜻하는 `char.persona`, 캐릭터 생성 화면의 성격/페르소나 필드, AI 프롬프트에 들어가는 캐릭터 설정
- 데이터 정책: 기존 `personas` 테이블과 저장 데이터는 삭제하지 않는다. 기존 페르소나로 생성된 DM 기록도 읽을 수 있게 유지한다.

### 관계의 의미

`char.relations` 원문은 캐릭터 설정 전체를 보존한다. 펫, 가족 설정, 사물처럼 실제 앱 캐릭터가 아닌 대상도 원문에서 삭제하지 않는다.

피드 관계 버튼, 호감도, 관계 진전처럼 캐릭터 간 상호작용이 필요한 기능에서는 아래 후보 중 이름이 일치하는 대상만 “연결된 캐릭터 관계”로 취급한다.

- 사용자의 다른 로컬 캐릭터
- 현재 팔로우한 캐릭터
- 서버에서 조회 가능한 공유 캐릭터

나중에 같은 이름의 캐릭터가 등록되거나 팔로우되면 별도 데이터 변환 없이 관계 UI에 자동으로 나타나야 한다.

## 4. 핵심 설계 결정

### 4.1 게시글은 백엔드 권위 데이터로 전환

백엔드 스케줄링만 추가하면 프런트 자동저장이 새 게시글을 덮어쓸 수 있다. 따라서 스케줄러보다 먼저 게시글 동시성 경계를 정리한다.

Phase 1에서는 기존 `Character.posts` JSON 구조를 유지하되 다음 규칙을 적용한다.

- `posts_revision`을 캐릭터별로 저장한다.
- 게시글 조회와 변경은 전용 API를 사용한다.
- 프런트의 구조화 상태 자동저장은 더 이상 `posts`를 덮어쓰지 않는다.
- 프런트 게시글 변경 함수는 현재 revision과 함께 저장한다.
- revision 충돌 시 최신 게시글을 다시 읽고 동일한 사용자 변경을 한 번 재적용한다.
- 백엔드 스케줄러는 캐릭터 행을 잠근 뒤 새 글을 추가하고 revision을 증가시킨다.

이 접근은 게시글 테이블 전체 정규화보다 변경 범위가 작으면서도 백엔드 생성과 프런트 편집 간 유실을 막는다. 게시글 검색, 무한 스크롤, 대규모 통계가 필요해질 때 별도 `character_posts` 테이블 전환을 다시 검토한다.

### 4.2 자율 생성 실행 구조

새 외부 큐나 별도 워커 제품은 도입하지 않는다. 현재 단일 FastAPI 컨테이너 구조에 맞춰 비동기 스케줄러 루프를 FastAPI lifespan에서 시작하고 종료한다.

```text
[FastAPI lifespan]
       |
       v
[30초마다 due 캐릭터 조회]
       |
       v
[FOR UPDATE SKIP LOCKED로 1건 claim]
       |
       +--> next_auto_post_at 선반영 및 commit
       |
       v
[서버 공통 피드 생성 서비스]
       |
       +--> Gemini 실패: 오류 상태 + 짧은 재시도 시각 기록
       |
       v
[Character.posts append + posts_revision 증가]
       |
       v
[공유 캐릭터 snapshot 동기화]
```

다중 프로세스나 다중 인스턴스가 생겨도 같은 캐릭터를 중복 처리하지 않도록 PostgreSQL 행 잠금의 `SKIP LOCKED`를 사용한다. FastAPI의 시작·종료 수명주기는 `lifespan`으로 관리한다.

스케줄 상태는 캐릭터별로 저장한다.

- `auto_post_enabled`: 자율 작성 활성화 여부
- `auto_post_interval_seconds`: 캐릭터별 자율 생성 주기 (`900`, `1800`, `3600` 중 하나)
- `next_auto_post_at`: 다음 실행 예정 시각
- `last_auto_post_at`: 마지막 성공 시각
- `last_auto_post_error`: 마지막 실패 요약
- `auto_post_failure_count`: 연속 실패 횟수
- `posts_revision`: 게시글 동시성 버전

기본 자율 생성 주기는 15분으로 두고, 캐릭터별로 `15분 / 30분 / 1시간` 중 하나를 선택할 수 있게 한다. 백엔드는 `900 / 1800 / 3600초`만 허용하며 그 외 값은 거부한다. 30초 테스트 주기는 제거한다.

### 4.3 사용 한도는 PostgreSQL에서 집계

다중 백엔드 인스턴스와 프로세스 재시작 이후에도 동일한 한도가 적용되도록 메모리 기반 사용량 집계를 PostgreSQL 기반 집계로 교체한다.

- 사용자별 일일 AI 호출 횟수를 날짜와 사용자 ID 기준으로 저장한다.
- 시스템 전체 월간 예상 비용을 연월 기준으로 저장한다.
- 한도 확인과 사용량 증가는 하나의 트랜잭션에서 처리한다.
- 일반 API 요청과 백엔드 자율 생성이 같은 집계를 사용한다.
- 한도 초과 시 Gemini를 호출하지 않고 게시글도 저장하지 않는다.
- 일일·월간 기간이 바뀌면 새 집계 행을 사용하며 이전 기록은 운영 감사용으로 보존한다.

### 4.4 피드 생성 규칙 단일화

백엔드 스케줄러와 사용자의 “캐릭터에게 시키기” 기능이 서로 다른 프롬프트를 사용하지 않도록 피드 글 생성 규칙을 백엔드 서비스로 옮긴다.

- `/api/ai/generate`는 DM과 캐릭터 분석 등 범용 생성 API로 유지한다.
- 게시글 생성은 캐릭터 ID를 기준으로 서버가 캐릭터 설정과 최근 글을 읽어 실행한다.
- 사용자가 분위기를 선택해 생성하는 흐름도 같은 백엔드 서비스를 호출한다.
- 자율 생성은 서버가 분위기를 선택한다.
- 생성 결과 파싱, 중복 방지 문맥, 저장, 공유 snapshot 갱신을 한 서비스 경계에서 처리한다.

### 4.5 사용자 페르소나는 중앙 기능 플래그로 비활성화

큰 JSX 블록을 주석으로 남기지 않는다. 중앙의 `USER_PERSONA_FEATURE_ENABLED = false` 플래그로 모든 사용자 진입점을 차단한다.

- 기능이 꺼져 있으면 발화자 기본값을 항상 현재 캐릭터로 정규화한다.
- 과거 상태에 `p:<persona_id>`가 남아 있어도 화면 진입 시 안전하게 `char`로 되돌린다.
- 기존 페르소나 대화방과 메시지는 삭제하지 않고 읽기 전용 과거 데이터로 유지한다.
- 백엔드 모델, 마이그레이션, 구조화 저장 계약은 Phase 1에서 제거하지 않는다.

- [ ] revision을 검사하는 게시글 저장 API를 추가한다.
- [ ] 자율 모드 활성화/비활성화 API를 추가한다.
- [ ] 캐릭터별 자율 생성 주기를 조회·변경할 수 있는 API를 추가하고 `900 / 1800 / 3600초`만 허용한다.
- [ ] 소유자 검증을 모든 캐릭터 게시글 API에 적용한다.
- [ ] 구조화 상태 upsert가 기존 `posts`를 더 이상 덮어쓰지 않게 한다.
- [ ] 피드 생성 프롬프트와 결과 파싱을 백엔드 서비스로 이동한다.
- [ ] PostgreSQL에 사용자별 일일 AI 사용량과 시스템 월간 예상 비용 집계 모델·마이그레이션을 추가한다.
- [ ] Gemini 서비스가 HTTP `Request` 없이도 사용자/스케줄러 사용량 키를 받을 수 있게 경계를 분리한다.
- [ ] 일반 AI API와 자율 생성 서비스가 같은 PostgreSQL 사용량 집계를 사용하게 한다.
- [ ] 한도 검사와 사용량 증가를 트랜잭션으로 처리해 동시 요청이 한도를 초과하지 않게 한다.
- [ ] 자율 생성 실행 전에 사용자별 일일 사용 한도와 전체 월간 비용 한도를 확인하고, 한도 초과 시 AI를 호출하거나 게시글을 생성하지 않는다.
- [ ] 사용 한도 초과는 일반 생성 실패와 구분해 기록하고, 다음 허용 시점 전까지 불필요하게 재시도하지 않는다.
- [ ] 게시글 생성 성공 시 로컬 캐릭터와 공유 캐릭터 snapshot을 함께 갱신한다.
- [ ] 게시글 생성 실패 문구를 게시글 본문으로 저장하지 않는다.

### Phase 1D. 백엔드 스케줄러

- [ ] FastAPI lifespan에서 비동기 스케줄러 task를 시작하고 종료 시 취소한다.
- [ ] 30초마다 due 캐릭터를 제한된 batch 크기로 조회한다.
- [ ] `FOR UPDATE SKIP LOCKED`로 캐릭터별 실행을 한 번만 claim한다.
- [ ] 외부 AI 호출 전에 다음 실행 시각을 선반영해 중복 호출을 막는다.
- [ ] 다음 실행 시각은 캐릭터별 `auto_post_interval_seconds`를 기준으로 계산한다.
- [ ] 성공 시 마지막 성공 시각과 실패 횟수를 갱신한다.
- [ ] 실패 시 오류 요약을 저장하고 지수형 재시도 간격을 적용하되 최대 15분을 넘지 않게 한다.
- [ ] 프로세스 재시작 시 DB의 `next_auto_post_at`을 기준으로 due 작업을 다시 찾는다.
- [ ] 앱이 닫혀 있어도 백엔드가 실행 중이면 생성되도록 한다.

### Phase 1E. 프런트 동기화

- [ ] 자율 모드 토글을 로컬 state가 아닌 백엔드 상태와 연결한다.
- [ ] 자율 생성 주기 설정 UI에 `15분 / 30분 / 1시간` 선택지를 제공하고 백엔드 상태와 연결한다.
- [ ] 카운트다운은 서버의 `next_auto_post_at`을 표시하는 읽기 전용 UI로 변경한다.
- [ ] 피드 진입 시 서버 게시글과 스케줄 상태를 조회한다.
- [ ] 앱이 foreground로 돌아올 때 최신 게시글을 다시 조회한다.
- [ ] 피드 화면이 열려 있을 때는 가벼운 주기 조회로 서버 생성 글을 반영한다.
- [ ] 게시글 생성, 직접 작성, 수정, 삭제, 좋아요, 댓글 변경을 revision 기반 저장 함수로 통합한다.
- [ ] revision 충돌 시 최신 상태를 읽고 사용자 변경을 한 번 재적용한다.
- [ ] 자동저장 payload에서 게시글 전체 배열을 제거한다.

### Phase 1F. 문서와 운영 설정

- [ ] 백엔드 환경설정에 스케줄러 활성화 여부, poll 주기, batch 크기, 기본 게시 주기 `15분`을 추가한다.
- [ ] 로컬 테스트에서는 스케줄러를 기본 비활성화해 테스트 수집 중 외부 AI가 호출되지 않게 한다.
- [ ] 백엔드 구조/API 문서와 기술 스택 문서를 갱신한다.
- [ ] 배포 환경에 스케줄러가 켜졌는지 확인할 운영 체크리스트를 작성한다.

## 6. Phase 2 작업: 외부 이미지 스토리지

Phase 1 검증과 안정화 후 별도 작업으로 진행한다. 스토리지 공급자는 구현 시작 전에 결정한다. 기본 추천은 S3 호환 오브젝트 스토리지이며, 실제 배포 환경·비용·CDN·비공개 이미지 요구사항을 비교해 선택한다.

```text
[앱에서 이미지 선택]
       |
       v
[백엔드 업로드 요청 + 소유권 검증]
       |
       v
[presigned upload URL 발급]
       |
       v
[앱 -> Object Storage 직접 업로드]
       |
       v
[object key/URL/metadata를 PostgreSQL에 저장]
       |
       +--> 프로필/갤러리/게시글/DM에서 URL 사용
       +--> 삭제 시 참조 확인 후 object 정리
```

### Phase 2A. 공급자와 보안 정책

- [ ] AWS S3, Cloudflare R2 등 후보의 비용, CDN, CORS, presigned URL 지원을 비교한다.
- [ ] 프로필/공개 게시글 이미지는 공개 CDN URL, DM 이미지는 만료되는 서명 URL을 기본 정책으로 검토한다.
- [ ] 허용 MIME type, 파일 크기, 픽셀 크기, 사용자별 quota를 정한다.
- [ ] object key에 사용자 ID와 캐릭터 ID를 포함하되 원본 파일명과 개인정보는 노출하지 않는다.

### Phase 2B. 업로드 API와 데이터 모델

- [ ] 삭제, 캐릭터 삭제, 계정 삭제 시 orphan object 정리 정책을 구현한다.

## 8. 실패 모드와 대응

| 실패 모드 | 대응 | 테스트 | 사용자에게 보이는 상태 |
|---|---|---|---|
| 두 backend worker가 같은 작업을 조회 | `FOR UPDATE SKIP LOCKED`와 next 시각 선반영 | 동시 claim 통합 테스트 | 중복 게시글 없음 |
| AI 호출 중 프로세스 종료 | claim된 next 시각 이후 다음 주기에 재개 | 재시작 복구 테스트 | 한 주기를 건너뛸 수 있으나 중복 없음 |
| Gemini timeout/제한 | 실패 횟수와 오류 저장, backoff | timeout/429 테스트 | 자율 모드 상태에 최근 실패 표시 |

## 9. 작업 순서와 의존성

| 순서 | 작업 | 선행 조건 |
|---|---|---|
| 1 | 시간 유틸 및 관계 바인딩 | 없음 |
| 2 | 페르소나·테스트 UI 비활성화 | 없음 |
| 3 | 게시글 revision 및 전용 API | 없음 |
| 4 | 피드 생성 규칙 백엔드 이동 | 게시글 API |
| 5 | 백엔드 스케줄러 | 생성 서비스, 게시글 API |
| 6 | 프런트 서버 동기화 | 게시글 API, 스케줄러 상태 API |
| 7 | 통합 테스트와 문서 | Phase 1 전체 |
| 8 | 외부 이미지 스토리지 | Phase 1 안정화, 공급자 결정 |

Phase 1의 1번과 2번은 독립적으로 진행할 수 있다. 3~6번은 게시글 권위 전환과 같은 상태 경계를 공유하므로 순차 구현한다.

## 10. 범위에서 제외

- 사용자 페르소나 DB 테이블과 기존 데이터 삭제: 임시 비활성화이므로 보존한다.
- 캐릭터 성격 필드인 `char.persona` 제거: 사용자 페르소나 기능과 다른 개념이다.
- 게시글을 별도 정규화 테이블로 전면 이전: Phase 1에서는 revision 기반 JSON 저장으로 동시성만 해결한다.
- Redis, Celery, 외부 메시지 큐 도입: 현재 규모와 단일 백엔드 구조에는 과하다.
- 자율 생성 주기의 임의 숫자 입력: `15분 / 30분 / 1시간`만 지원한다.
- 팔로잉 캐릭터의 자율 게시글을 현재 사용자의 스케줄러가 대신 생성: 각 캐릭터 소유자의 자율 설정만 실행한다.
- Phase 1에서 base64 이미지 형식을 제거: 외부 스토리지 전환과 함께 Phase 2에서 처리한다.
- 이미지 생성 AI 도입: 이번 범위는 저장과 전달 경계만 다룬다.

- [ ] 캐릭터별 자율 생성 주기를 `15분 / 30분 / 1시간` 중 하나로 변경하면 다음 실행 예정 시각과 이후 생성 주기에 반영된다.

- [ ] 다중 worker에서도 같은 캐릭터의 게시글이 중복 생성되지 않는다.

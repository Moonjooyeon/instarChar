# ALIVE 앱인토스 출시 주의사항 및 운영 가드레일

## 목적과 적용 범위

이 문서는 `alive`를 앱인토스 미니앱으로 출시할 때 지켜야 할 제품·운영·기술 기준을 정리한다. 기존 App Store·Google Play 독립 앱에는 앱인토스의 로그인·외부 링크·결제 제한을 적용하지 않는다. 다만 AI 안전 및 사용자 보호 기준은 모든 배포 환경에서 일관되게 적용한다.

> **정책 확인일: 2026-07-29.** 앱인토스 정책은 수시로 바뀔 수 있으므로, 출시 검수 요청 직전에도 원문을 다시 확인한다. 이 문서는 법률 자문이나 토스의 사전 승인을 대체하지 않는다.

## 출시 판단

`alive`는 AI 캐릭터가 피드·댓글·캐릭터 간 대화를 생성하는 서비스이므로, 생성형 AI 서비스의 고지·표시 의무와 AI 채팅·상담 안전 기준을 핵심 출시 요건으로 본다. 실제 이용자 간 랜덤 매칭, 공개 프로필 기반 메시지, 실제 이용자 간 1:1 DM을 제공하지 않는다면 만남·소개팅 서비스로 분류될 가능성은 낮다. 단, 최종 분류는 토스의 사전 검토 결과를 따른다.

## 배포 환경별 분리 원칙

| 항목 | 앱인토스 미니앱 | App Store·Google Play 독립 앱 |
| --- | --- | --- |
| 로그인 | 토스 로그인만 사용 | Google·Apple 로그인 유지 가능 |
| 결제 | 디지털 상품은 앱인토스 인앱결제만 사용 | 각 스토어 정책에 맞는 결제 사용 |
| 외부 이동 | 설치 유도·외부 가입·외부 결제 흐름 금지 | 제품 정책에 따라 운영 |
| 광고 | 앱인토스가 제공하는 광고 형식만 사용 | 제품 정책에 따라 운영 |
| 사용자 계정 | 토스 로그인 식별자로 생성·관리 | 기존 Google·Apple 식별자로 생성·관리 |

앱인토스 빌드에서는 Google·Apple 로그인 버튼, OAuth URL, 외부 앱 다운로드 링크를 표시하거나 호출하지 않는다. 독립 앱의 기존 로그인 기능을 유지하기 위해서는 배포 대상에 따라 UI와 인증 제공자를 명시적으로 분기한다.

## 반드시 충족할 생성형 AI 기준

### 사용자에게 보여줄 기준

- [ ] 첫 서비스 진입 또는 최초 AI 기능 사용 시, "이 서비스의 캐릭터·피드·댓글·대화는 생성형 AI를 활용해 만들어질 수 있어요"와 같이 AI 사용 사실을 고지한다.
- [ ] AI가 생성한 피드, 댓글, 캐릭터 간 대화, 이미지 등에는 사용자가 즉시 알아볼 수 있는 `AI 생성` 라벨 또는 배지를 표시한다.
- [ ] 사용자가 AI 결과물을 수정한 경우에도, 원본이 AI로 생성됐는지 판단할 수 있는 표시 기준을 정한다.
- [ ] 캐릭터가 실제 사람·실제 사용자로 오인되지 않도록 가상 AI 캐릭터임을 서비스 소개와 주요 화면에서 명확히 안내한다.

### 생성·운영 기준

- [ ] 사용자 입력과 AI 출력 모두에서 선정성, 폭력·자해, 혐오·차별, 불법·범죄 조장, 개인정보 노출 위험을 문맥까지 고려해 필터링한다.
- [ ] 금지 요청에는 우회 요청까지 포함해 일관되게 거절하는 응답을 제공한다.
- [ ] 자해·자살 관련 발화가 감지되면 생성 제한과 안전 안내를 제공한다.
- [ ] 부적절한 생성 결과를 신속히 수정·차단할 수 있는 운영자 절차와 책임자를 둔다.
- [ ] AI 모델 또는 핵심 프롬프트를 바꾸기 전, 앱인토스 배포 검토가 필요한지 확인하고 변경 이력을 남긴다.
- [ ] 독립 앱·웹에서도 동일 모델을 쓴다면 최소한의 안전 기준을 동일하게 적용한다.

현재 프로젝트에는 신고·차단·운영자 검토 API와 일부 문자열 기반 위험 콘텐츠 차단이 있다. 앱인토스 출시 전에는 위 체크리스트 수준의 문맥 기반 필터링, 안전 응답, 운영 절차가 실제로 작동하는지 별도로 검증해야 한다.

## 외부 이동과 독립 앱 홍보 금지

앱인토스 안에서 독립 앱 설치를 권유하거나, 더 많은 기능을 이용하려면 App Store·Google Play 앱을 설치하라고 안내할 수 없다. 다음은 미니앱 빌드에서 제거하거나 표시하지 않는다.

- [ ] App Store·Google Play 다운로드 버튼과 스토어 링크
- [ ] "앱 설치 시 더 많은 기능", "앱 전용 혜택" 같은 설치 유도 문구·배너
- [ ] 외부 웹사이트에서 가입·로그인·결제를 완료하라는 흐름
- [ ] 자사 웹사이트로 연결되는 공유 링크
- [ ] 미니앱 안에서 끝나지 않고 외부 페이지에 의존하는 핵심 기능

법률상 필수 고지 등 제한적으로 허용될 수 있는 외부 링크도 출시 전에 목적과 URL을 검토한다. 토스 미니앱용 공유 기능은 자사 웹 URL이 아니라 `intoss://` 기반의 토스 앱 링크를 사용한다.

## 로그인과 계정 관리

- [ ] 미니앱에서는 토스 로그인만 구현한다. Google, Apple, 이메일, 자체 회원가입·로그인은 제공하지 않는다.
- [ ] 토스 로그인 API 사용 전에 사업자 등록 가능 여부를 확인하고, 콘솔에서 mTLS 인증서와 키를 발급받는다.
- [ ] 인증서·키·복호화 키를 코드 저장소나 클라이언트 번들에 넣지 않고 배포 환경의 비밀 저장소에 보관한다.
- [ ] 기존 Google·Apple 사용자를 토스 사용자와 이메일만으로 자동 병합하지 않는다.
- [ ] 계정 연결 또는 기존 데이터 이전이 필요하면, 구현 전에 앱인토스 운영 채널로 허용 가능한 사용자 흐름을 문의한다.
- [ ] 토스 로그인의 연결 해제·약관 철회·토스 회원 탈퇴 콜백을 처리해 미니앱 세션을 종료한다.

토스 로그인, 결제, 기능성 알림, 프로모션 API는 서버와 앱인토스 간 mTLS 통신이 필요하다. 미니앱 로그인 도입은 프런트 버튼 변경만으로 끝나지 않으며, FastAPI 백엔드의 토스 사용자 공급자·서버 인증·세션 발급 구현이 필요하다.

## 결제·광고·수익화

- [ ] 초기 토스 MVP가 무료라면, 외부 결제와 결제 유도 UI를 넣지 않는다.
- [ ] 프리미엄 기능, 구독, 콘텐츠 이용 권한 같은 디지털 상품은 앱인토스 인앱결제로만 판매한다.
- [ ] 실물 상품이 생기는 경우에는 토스페이만 사용한다.
- [ ] 외부 PG, 외부 광고 네트워크, 외부 결제창을 미니앱에 연결하지 않는다.
- [ ] 인앱 광고를 넣는다면 앱인토스가 제공하는 전면형·보상형·배너 광고만 사용한다.
- [ ] 유료 기능·구독을 도입하기 전 환불, 해지, 고객 문의 및 분쟁 처리 정책을 준비한다.

## 콘텐츠·대화 운영 기준

캐릭터 간 대화라도 AI가 생성한 메시지는 사용자 안전과 민감 콘텐츠 기준의 적용 대상이 될 수 있다. 실제 이용자 간 메시지 기능을 나중에 추가하면 일반 채팅 서비스 또는 만남·소개팅 서비스의 별도 요건이 적용될 수 있으므로, 출시 전 운영 채널에 재확인한다.

- [ ] 피드, 댓글, DM 메시지별 신고 진입점을 제공한다.
- [ ] 사용자 또는 콘텐츠 차단 기능을 제공하고, 차단 결과가 피드·DM에 반영되게 한다.
- [ ] 신고 접수, 우선순위 판단, 제재, 이의제기, 재발 방지의 운영 절차를 문서화한다.
- [ ] 금지 콘텐츠와 이용 제한 기준을 이용약관·커뮤니티 정책에 명시한다.
- [ ] DM·콘텐츠 로그의 보관 범위, 접근 권한, 탈퇴 시 삭제 기준을 개인정보처리방침에 명시한다.
- [ ] 민감 표현을 포함한 캐릭터 설정·생성 결과를 테스트 케이스로 만들고, 출시 전 반복 검증한다.

## 추가 준비 항목

### 콘솔·사업자·고객 지원

- [ ] 토스 로그인을 쓸 계획이면 사업자 등록을 먼저 완료한다. 사업자 없이 미니앱 자체는 출시할 수 있지만, 토스 로그인·인앱결제·광고·프로모션·토스페이는 사용할 수 없다.
- [ ] 실제로 모니터링하는 고객 문의 이메일을 앱 정보에 등록하고, 문의 접수·응답 책임자와 비상 연락 방법을 정한다.
- [ ] 이용약관, 개인정보처리방침, 커뮤니티 운영정책, AI 이용 고지의 내용이 서로 충돌하지 않게 검토한다.
- [ ] 서비스 설명, 카테고리, 스크린샷이 실제 출시 기능과 일치하는지 확인한다. 기능을 과장하는 마케팅 소재는 사용하지 않는다.
- [ ] AI 캐릭터 대화·UGC·계정 이전·유료 기능 범위를 적은 사전 검토 문의를 채널톡으로 보낸다.

### 디자인과 사용자 경험

현재 앱인토스 FAQ는 미니앱을 라이트 모드 기준으로 디자인·개발·출시하도록 안내한다. 현재 `alive`의 어두운 보라 테마는 독립 앱에서는 유지하되, 미니앱용으로는 라이트 모드 기반의 전용 테마를 준비하고 샌드박스에서 표시를 확인한다. 고정 다크 테마를 유지하고 싶다면 구현 전에 채널톡으로 허용 범위를 확인한다.

- [ ] 토스 디자인 시스템(TDS)과 앱인토스 UI/UX 가이드를 기준으로 미니앱 전용 화면을 설계한다.
- [ ] 진입 즉시 강제 바텀시트, 뒤로 가기를 막는 이탈 방지 모달, 예상하지 못한 광고, 의미가 불명확한 CTA 등 다크패턴을 넣지 않는다.
- [ ] 사용자가 토스와 `alive`를 혼동하지 않도록 `ALIVE`의 로고·이름·브랜드 색상을 지속적으로 표시한다.
- [ ] 미니앱의 기본 내비게이션 바를 중복 구현하지 않고 SDK 제공 동작과 충돌하지 않게 한다.
- [ ] 앱 로고와 스크린샷은 콘솔의 필수 픽셀 규격, 배경, 실제 기능 노출 기준에 맞는 파일만 사용한다.

### 기술·데이터 보존·보안

- [ ] 앱인토스 전용 WebView SDK 2.x 빌드 경로를 만들고, 독립 앱의 Capacitor 빌드와 분리한다.
- [ ] FastAPI API 서버의 CORS 허용 목록에 앱인토스에서 요구하는 도메인을 추가하고, 토스 샌드박스에서 실제 요청을 확인한다.
- [ ] 캐릭터·피드·대화 등 사용자 데이터는 자체 서버에 저장한다. 앱인토스 Storage는 앱 삭제 또는 기기 변경 후 유지되지 않을 수 있다.
- [ ] 토스 로그인 API에 필요한 mTLS 인증서·키를 서버 비밀 저장소에 보관하고, 만료 교체 일정과 담당자를 정한다.
- [ ] 토스용 사용자 공급자(`toss`)와 기존 Google·Apple 사용자 공급자를 분리해 보관하고, 자동 계정 병합을 하지 않는다.
- [ ] 클라이언트 오류 추적 도구와 운영 로그를 준비해 샌드박스·실서비스 오류를 재현할 수 있게 한다.
- [ ] 출시 번들은 압축 해제 기준 100MB 이하인지 확인한다.

### 검수와 운영 준비

- [ ] 브라우저만으로 승인 판단을 하지 않는다. 검수 요청 전 토스 샌드박스 앱에서 로그인, 라우팅, 뒤로 가기, 네트워크 오류, 재진입을 테스트한다.
- [ ] AI 생성 실패, 네트워크 끊김, 로그인 연결 해제, 탈퇴, 신고·차단, 금지 요청을 포함한 수동 QA 시나리오를 만든다.
- [ ] 출시 검수는 서비스·기능·디자인·보안을 함께 본다. 각 항목의 증빙 화면과 테스트 계정을 준비한다.
- [ ] 검수 중에는 하나의 번들 버전만 진행할 수 있으므로, 오류가 발견되면 검토 요청을 취소하고 수정 번들을 다시 올리는 절차를 숙지한다.
- [ ] 출시 후에도 AI 프롬프트·모델·수익화·외부 링크 등 주요 변경은 정책 재검토 대상으로 취급한다.

출처: [앱인토스 FAQ — 샌드박스와 출시 검수](https://developers-apps-in-toss.toss.im/faq.html)

## 권장 실행 순서

1. 채널톡 사전 검토로 AI 캐릭터 대화·UGC·계정 이전 정책을 확인한다.
2. 토스 로그인이 필요한지 결정하고, 필요하다면 사업자 등록과 mTLS 인증서 발급 준비를 시작한다.
3. 라이트 모드 기반의 앱인토스 전용 화면과 AI 고지·`AI 생성` 라벨을 디자인한다.
4. 앱인토스 전용 빌드·토스 로그인·CORS·서버 저장을 구현한다.
5. 샌드박스에서 핵심 사용자 흐름과 안전·오류 시나리오를 검증한다.
6. 스크린샷·약관·고객 문의·운영정책을 최종 점검한 뒤 출시 검수를 요청한다.

## 출시 전 필수 확인 목록

- [ ] 앱 정보의 서비스 설명과 실제 기능이 일치한다.
- [ ] 앱인토스용 빌드에는 토스 로그인만 노출되고 Google·Apple·외부 가입 흐름이 없다.
- [ ] 첫 사용 AI 고지와 모든 AI 생성 결과의 표시가 구현됐다.
- [ ] AI 안전 테스트와 신고·차단·운영자 조치 흐름을 검증했다.
- [ ] 외부 앱 설치·앱마켓·자사 웹 홍보 링크가 없다.
- [ ] 결제·광고를 사용한다면 앱인토스 허용 방식만 사용한다.
- [ ] mTLS 인증서·키·복호화 키가 서버 비밀 저장소에만 있고, 만료 교체 책임자가 정해졌다.
- [ ] 토스 샌드박스 앱에서 로그인·핵심 사용자 흐름·오류 처리를 테스트했다.
- [ ] 채널톡으로 AI 캐릭터 대화, UGC, 유료 기능 계획에 대한 사전 검토를 요청했다.
- [ ] 출시 검수 요청 직전에 공식 정책과 서비스별 주의사항의 최신 변경 사항을 다시 확인했다.

# 핵심 기능 및 저장 흐름 점검

## 범위

- 캐릭터 생성, 삭제, 앱 상태 저장 및 재수화 코드 경로
- 피드, 공유·팔로우, DM, 페르소나의 변경·삭제 경로
- FastAPI 캐릭터 삭제 API와 관련 데이터 정리
- 정적 검증 및 기존 도메인 테스트

## 확인된 문제와 조치

| 우선순위 | 문제 | 영향 | 근거 |
|---|---|---|---|
| P1 | 마지막 캐릭터를 삭제해도 로컬 스냅샷이 이전 계정 목록을 유지한다. | 앱을 다시 열면 삭제한 캐릭터가 재표시된다. | 빈 `accounts`도 저장하고, 프로필 백업을 항상 갱신하며, 성공한 빈 구조화 목록은 캐시를 비우도록 수정했다. |
| P2 | 삭제 요청의 네트워크 예외가 처리되지 않는다. | UI와 서버 상태가 달라질 수 있다. | 원격 삭제 성공 뒤에만 UI를 변경하고, 실패 시 기존 캐릭터를 유지하며 실패 상태를 표시하도록 수정했다. |
| P2 | 캐릭터 삭제 흐름을 검증하는 상태 전이 테스트가 없다. | 현재 테스트가 이 회귀를 막지 못한다. | API 요청 단위 테스트와 백엔드 라우트 모킹 테스트만 존재하며, 마지막 계정 삭제·재수화·실패 시나리오는 없다. |
| P1 | 공유 DM을 참여자 한 명이 삭제하면 모든 참여자의 서버 대화방이 삭제된다. | 다른 참여자의 기록이 함께 지워진다. | 공유 DM 삭제와 계정 삭제 모두 요청한 사용자를 참여자 목록에서만 제거하도록 수정했다. |
| P1 | 팔로우 API의 `ok: false` 응답을 프런트가 성공으로 처리한다. | 팔로우 UI와 서버 상태가 어긋난다. | 응답 본문의 `ok`를 읽고, 거절·통신 실패 시 팔로잉 목록과 타임라인을 복구하도록 수정했다. |
| P2 | 페르소나 삭제가 구조화 저장소에서 제거되지 않고, 빈 응답도 캐시를 비우지 않는다. | 삭제한 페르소나가 재실행 후 복원될 수 있다. | 서버 동기화에서 누락된 페르소나를 삭제하고, 성공한 빈 목록은 클라이언트 상태를 비우도록 수정했다. |
| P2 | 여러 삭제 동작이 원격 요청 실패를 사용자에게 명확히 알리거나 되돌리지 않는다. | 일시적 네트워크 오류 뒤 화면과 서버 상태가 달라질 수 있다. | 캐릭터 삭제는 UI 상태를 먼저 변경하고, DM 삭제는 원격 오류를 콘솔에만 기록한 뒤 로컬 상태를 저장한다. |

## 재현 절차

1. 캐릭터를 하나만 생성한다.
2. 홈 화면에서 해당 캐릭터를 삭제한다.
3. 앱을 새로고침하거나 종료 후 다시 연다.
4. 이전 로컬/프로필 백업을 기반으로 캐릭터가 다시 보일 수 있다.

## 정상 동작으로 확인한 항목

- `DELETE /api/characters/{source_account_id}`는 캐릭터, 공유 캐릭터, 해당 캐릭터의 팔로우 행, 소유자 DM을 정리하고 커밋한다.
- 캐릭터 생성은 전용 `PUT /api/characters/{source_account_id}`를 통해 저장되며, 핸들 고유성 충돌을 처리한다.
- 하나 이상 남은 캐릭터를 삭제하는 경우에는 비어 있지 않은 스냅샷을 저장하므로 마지막 캐릭터 삭제와는 다른 경로를 탄다.
- 피드 게시물은 서버의 revision으로 충돌을 감지하고, 충돌 시 최신 상태를 읽어 한 번 재시도한다.
- 캐릭터 생성·수정은 서버에서 전역 고유 핸들을 최종 검증하며, 공유 캐릭터 스냅샷도 소유 캐릭터의 핸들을 사용한다.
- 피드의 공개 게시물 좋아요는 서버 결과로 낙관적 UI를 되돌리고, 중복 요청을 막는다.

## 공유 DM 삭제의 영향

1. 사용자가 공유 DM에서 삭제를 선택한다.
2. 클라이언트는 `DELETE /shared-dm-threads?thread_key=...`를 요청한다.
3. 서버는 요청자를 참여자로 확인한 뒤 그 사용자를 참여자 목록에서만 제거한다.
4. 다른 참여자는 기존 대화와 메시지를 유지하고, 마지막 참여자가 나갈 때만 행을 삭제한다.

계정 삭제도 동일하게 처리하므로, 탈퇴한 사용자의 공유 DM 정리가 다른 참여자의 기록을 지우지 않는다.

## 적용한 수정

1. 빈 캐릭터 목록을 모든 저장 경로에서 정상 상태로 저장·복원한다.
2. 캐릭터 삭제는 서버 삭제 성공 후 UI에 반영하고, 실패하면 기존 상태를 유지한다.
3. 공유 DM 삭제·계정 삭제는 다른 참여자의 메시지를 보존한다.
4. 팔로우 거절·실패를 서버 응답으로 판정하고 낙관적 UI를 되돌린다.
5. 페르소나 동기화는 서버의 삭제와 빈 목록 재수화를 지원한다.

- `npm run typecheck`: 통과
- `npm run test:domain`: 123개 통과
- `npm run build`: 통과
- `python3 -m compileall`: 통과
- 백엔드 테스트: 저장소에 안내된 `backend/.venv/bin/pytest` 실행 파일이 없어 실행하지 못했다.
- E2E: 실행 중인 앱이 이 작업에 연결돼 있지 않아 실행하지 않았다. 현재 E2E는 대부분 API 모킹을 사용하므로 실제 서버 데이터 삭제·공유 DM·팔로우 거절은 검증하지 않는다.

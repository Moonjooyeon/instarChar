# 앱인토스 인앱결제 배포 및 운영 가이드

## 목적

`alive`의 Apps in Toss 일회성 인앱결제를 안전하게 배포하고, 제한 활성화부터 전체 공개, 장애 차단, 미지급 복원과 환불 재조정까지 같은 절차로 운영한다. 실제 인증서·키·토스 사용자 식별키는 이 문서와 저장소에 기록하지 않는다.

## 제어 계층

| 제어 | 성격 | OFF일 때 | 유지해야 하는 기능 |
| --- | --- | --- | --- |
| 콘솔 상품 노출 | 제공자 측 강한 차단 | SDK 상품 목록과 신규 구매에서 제외 | 이미 발생한 주문의 서버 조회·환불 |
| `TOSS_IAP_PURCHASE_ENABLED` | 앱의 신규 구매 전역 스위치 | 카탈로그의 구매 버튼 비활성화 | SKU 전달, 미결 주문 복원·환불 |
| `TOSS_IAP_PURCHASE_ROLLOUT_PERCENT` | 토스 사용자별 결정적 0~100% 앱 게이트 | 0이면 모든 신규 구매 버튼 비활성화 | 기존 결제 복원·재조정 |
| `TOSS_IAP_ENABLED` | 주문 검증·지급·복원 통합 스위치 | 지급과 복원 API 중단 | 장애 롤백 중에는 원칙적으로 ON 유지 |
| `TOSS_IAP_RECONCILIATION_ENABLED` | 서버 주문 재조회 | 자동 지급·환불 재조정 중단 | 신규 구매 차단 중에도 ON 유지 |
| `TOSS_IAP_AUDIT_ALERTS_ENABLED` | 재무 감사 오류 신호 | 자동 `iap_integrity_alert` 미발행 | 보호된 감사 API는 계속 사용 가능 |

퍼센트 롤아웃은 `TOSS_IAP_SUBJECT_HMAC_KEY`와 토스 사용자 식별키로 안정적인 코호트를 계산한다. 같은 키와 퍼센트에서는 같은 사용자가 같은 결과를 받는다. HMAC 키를 바꾸면 롤아웃 코호트와 탈퇴·재가입 구매 이력 연결이 함께 바뀌므로 운영 중 임의 교체하지 않는다.

퍼센트 롤아웃은 앱 카탈로그와 버튼을 제어하는 방어 계층이다. 이미 SKU를 아는 구버전 또는 변조 클라이언트의 제공자 주문 생성을 완전히 차단하는 수단으로 간주하지 않는다. 실제 신규 판매를 확실히 멈출 때는 콘솔 상품 노출 OFF도 함께 사용하며, 결제가 이미 완료된 주문은 사용자 손실을 막기 위해 서버가 계속 검증·지급한다.

신규 구매 ON은 재조정과 감사 경보가 모두 ON일 때만 서버 시작 검증을 통과한다. 클라이언트도 미지급 복원과 지급 완료 확인이 모두 가능한 Android 토스 앱 5.234.0·iOS 5.233.0 이상에서만 구매를 허용한다. 콘솔 상품의 `최소 지원 버전`은 이 토스 앱 버전이 아니라 업로드한 미니앱 번들 버전이다.

## 환경별 권장값

| 단계 | IAP | 신규 구매 | 롤아웃 | 재조정 | 감사 경보 | 콘솔 노출 |
| --- | --- | --- | ---: | --- | --- | --- |
| 설정 준비 | ON | OFF | 0 | ON | ON | OFF |
| 샌드박스 실행 시간 | ON | ON | 100 | ON | ON | 테스트 상품만 ON |
| 운영 초기 공개 | ON | ON | 10 | ON | ON | 승인 상품 ON |
| 확대 관찰 | ON | ON | 25 → 50 | ON | ON | 승인 상품 ON |
| 전체 공개 | ON | ON | 100 | ON | ON | 승인 상품 ON |
| 장애 차단 | ON | OFF | 0 | ON | ON | OFF |

운영 초기 `10%`는 기본 제안이다. 실제 사용자 수가 적어 관찰 가능한 코호트가 생기지 않으면 제품·운영 승인 후 조정한다. 퍼센트 변경은 배포 변경 기록에 이전 값, 새 값, 변경 시각, 승인자를 남긴다.

## 최초 배포 순서

1. 데이터베이스 백업과 migration current/head를 확인한다.
2. migrations `0021`·`0022`·`0023`과 백엔드 코드를 배포한다.
3. 다섯 콘솔 SKU, mTLS 인증서·키, 전용 HMAC 키를 비밀 저장소에 주입한다.
4. `IAP=ON`, 신규 구매 `OFF`, 롤아웃 `0`, 재조정·감사 경보 `ON`으로 시작 단계 설정 검증을 통과시킨다.
5. `GET /api/moderation/credit-purchases/audit` 결과의 `purchases`와 `accounts`가 비어 있는지 확인한다.
6. 검증할 `.ait`를 콘솔 `앱 출시`에 업로드하고 배포 ID·QR을 기록한다.
7. 업로드 버전을 상품 `최소 지원 버전`으로 선택해 상품을 소모품·노출 OFF로 등록한다.
8. [콘솔 매니페스트 예시](../qa/guides/apps-in-toss-iap-console-manifest.example.json)를 증거 폴더에 복사해 실제 값을 채우고 사전 검증을 통과시킨다.
9. 샌드박스 시간에만 신규 구매 `ON`, 롤아웃 `100`, 테스트 상품 노출 ON으로 전환한다.
10. 정상 결제, 서버 지급 실패 복원, 오류, 반복 요청, 환불, 사용자 결제 내역과 기기 변경 시나리오를 증빙한다.
11. 모든 게이트 승인 후 운영 초기 공개 값을 적용하고 24시간 이상 관찰한다.

완성한 매니페스트에는 인증서, 개인키, HMAC 키나 운영 API 키를 넣지 않는다. 스테이징의 실제 `TOSS_IAP_CREDIT_*_SKU` 환경 변수가 주입된 셸에서 다음 명령을 실행한다.

```bash
make iap-release-check IAP_RELEASE_MANIFEST=documents/qa/evidence/apps-in-toss-iap-console-manifest.json
```

`passed for 5 products`가 출력되지 않으면 상품 노출과 신규 구매를 켜지 않는다. 검증기는 `.ait` SHA-256·내부 배포 ID·앱 이름, 콘솔/최소 지원 버전, SKU, 공급가·판매가·표시가격, 지급량, 승인 문구, PNG 크기·해시와 노출 OFF를 검사한다.

## 탈퇴 계정 구매기록

- 계정 삭제 요청 후 7일 동안은 계정과 구매 원장을 유지해 재로그인 복구를 허용한다.
- 최종 파기 시 Apps in Toss `remove-by-user-key`를 mTLS로 호출한다. 실패하면 사용자 행을 삭제하지 않고 스케줄러 재실행 대상으로 남긴다.
- 최종 파기 트랜잭션은 구매행의 `retention_until`을 `max(거래일+5년, 파기 시각)`으로 설정하고 사용자 FK를 제거한다.
- 계정 삭제 스케줄러는 `user_id IS NULL`이고 보존 만료가 지난 구매행 전체를 삭제한다.
- 분쟁·수사·법적 보존 정지가 필요하면 만료 전에 `retention_until`을 연장하고 주문 ID, 근거, 승인자, 새 만료일을 접근 통제된 운영 기록에 남긴다.
- HMAC, 원문 `userKey`, 인증서, 액세스 토큰을 고객지원 티켓이나 일반 로그에 복사하지 않는다.

보존 기간과 고객 노출 문구의 승인 상태는 [구매기록 보존 및 탈퇴 처리 결정](../plans/release/store/decision_apps-in-toss-iap-purchase-retention_2026-08-11.md)을 따른다. 법무·대표자 승인과 공개 약관 개정 전에는 신규 결제를 활성화하지 않는다.

## 확대 게이트

각 단계에서 다음 조건을 모두 만족한 뒤에만 롤아웃을 높인다.

- `iap_integrity_alert`가 없다.
- 재조정 poll·주문 단위 예외가 없다.
- 보호된 감사 API의 `purchases`, `accounts`가 비어 있고 `truncated=false`다.
- 콘솔 결제 완료·환불 건과 내부 구매·chargeback 원장이 일치한다.
- 결제 완료 후 미지급 문의와 중복 지급이 없다.
- SDK `displayAmount`와 콘솔 VAT 포함 판매가가 일치한다.
- 운영·재무·고객지원 담당자가 다음 단계 확대를 승인했다.

한 조건이라도 충족하지 못하면 퍼센트를 높이지 않는다. 지급·환불 정합성 문제면 즉시 장애 차단 값으로 전환한다.

## 모니터링 규칙

애플리케이션 로그 수집 시스템에서 다음 패턴을 경보로 등록한다.

| 로그 패턴 | 심각도 | 의미 | 1차 행동 |
| --- | --- | --- | --- |
| `iap_integrity_alert` | critical | 장기 미지급, 검토·실패, 구매·환불 원장 또는 계정 잔액 불일치 | 신규 구매 차단 후 감사 API 조회 |
| `Credit purchase reconciliation failed` | critical | 특정 주문의 서버 재조회·지급·환불 처리 실패. 원본 주문 ID는 로그에 포함되지 않음 | 처리 큐·감사 API에서 후보를 찾고 보호된 주문 상세로 제공자 상태 재확인 |
| `Credit purchase reconciliation poll failed` | critical | 재조정 배치 자체 실패 | DB·mTLS·토스 API 상태 확인 |
| IAP 시작 설정 `ValueError` | critical | SKU, HMAC, mTLS 또는 플래그 조합 오류 | 서버를 억지로 기동하지 말고 설정 복구 |

`iap_integrity_alert`와 주문별 재조정 예외에는 원본 주문 ID나 사용자 ID를 넣지 않는다. 무결성 경보에는 구매·계정 후보 수, `truncated`와 사유별 건수만 들어간다. 상세 정보는 `X-Moderation-Key`를 로그에 남기지 않고 보호된 처리 큐·감사·주문 상세 API로 조회한다.

경보 시스템에는 담당 채널, 주·부 담당자, 10분 이내 확인 기준과 에스컬레이션 대상을 등록한다. 애플리케이션 코드가 오류 로그를 내보내는 것만으로 외부 알림 설정이 완료된 것으로 판정하지 않는다.

## 장애 대응

1. `TOSS_IAP_PURCHASE_ENABLED=false`, 롤아웃 `0`, 콘솔 상품 노출 OFF로 신규 구매를 차단한다.
2. `TOSS_IAP_ENABLED`, 재조정과 감사 경보는 ON으로 유지한다.
3. `/api/moderation/credit-purchases/audit`와 상태 큐에서 영향 주문을 찾는다.
4. 주문 상세에서 최근 제공자 상태, 구매·chargeback 원장, 잔액과 부채를 대조한다.
5. `PAYMENT_COMPLETED/processing`은 자동 재조정 또는 같은 멱등 지급 API로 복원한다.
6. `review`, SKU 불일치, 원장 불일치는 증거를 보존하고 수동 잔액 조정 없이 담당자에게 이관한다.
7. 원인을 수정하고 감사 결과가 깨끗해진 뒤 샌드박스 회귀부터 다시 수행한다.

사용자에게 결제 완료 주문의 재구매를 먼저 권하지 않는다. 제공자 결제 상태가 불명확한 상태에서 임의 지급·차감·탕감을 수행하지 않는다.

## 인증서 교체

1. 현재 인증서의 만료일과 담당자를 월 1회 확인한다.
2. 만료 30일 전 새 인증서·키를 비밀 저장소에 준비한다.
3. 신규 구매를 차단한 상태에서 새 인증서로 주문 상태 조회를 검증한다.
4. 미결 주문 복원과 재조정이 통과한 뒤 운영 경로를 전환한다.
5. 이전 인증서는 복구 관찰 기간 후 폐기하고 폐기 시각과 담당자를 기록한다.

현재 애플리케이션은 한 쌍의 인증서·키 경로를 사용하므로 같은 프로세스에서 두 인증서를 동시에 선택하는 기능은 없다. 인프라의 원자적 secret 교체와 애플리케이션 재기동 절차를 실제 배포 환경에서 검증해야 한다.

## 증거와 변경 기록

- 번들 파일명, 앱 코드 커밋, 배포 ID와 SHA-256
- 백엔드 커밋, migration current/head와 배포 시각
- 플래그·롤아웃 이전값과 새 값, 승인자
- 콘솔 상품 SKU·공급가·판매가·최소 지원 버전·노출 상태
- 샌드박스 시나리오별 화면과 비식별 서버 로그
- 확대 단계별 감사 결과와 콘솔·원장 대조 결과
- 장애 발생·차단·복구 시각과 영향 주문 수

실제 비밀값, 원문 토스 userKey, 세션 쿠키와 개인키는 증거에 포함하지 않는다.
